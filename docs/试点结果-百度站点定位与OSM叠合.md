# 百度站点定位与 OSM 路网叠合试点报告

日期：2026-10-19  
项目：武汉个性化等时圈与区位评估平台  
试点线路：公交 340 路、公交 H89 路

## 一、试点目的

验证以下链路是否可行：

```text
武汉公交线路站点表
    → 百度地点检索补充站点坐标
    → 多候选筛选与线路连续性校验
    → BD-09 转 WGS84
    → 吸附到 OSM 可行驶道路
    → 输出叠合图与质量清单
```

同时评估百度 POI 对武汉中心城区和郊区公交站的覆盖差异，为全量 694 条线路的处理方案提供依据。

## 二、数据与工具

| 项目 | 内容 |
|---|---|
| 公交站点来源 | 武汉市公共数据平台《公交线路站点信息_2026-10-01》 |
| 站点表结构 | 一行一条线路，`tkzd` 字段按顿号分隔记录站序 |
| 试点规模 | 340 路 23 站；H89 路 56 站 |
| 路网 | 湖北 OSM GPKG，`gis_osm_roads_free` 图层 |
| 百度服务 | 地点检索 `place/v2/search`；地理编码 `geocoding/v3` |
| 坐标转换 | BD-09 → GCJ-02 → WGS84 |
| 路网吸附 | 仅使用 trunk/primary/secondary/tertiary/residential/service 等可行驶道路 |
| Python 环境 | 项目 `.venv`，GeoPandas、Shapely、PyProj、Pyogrio、Pandas、Matplotlib |

百度服务测试返回 `status=0`，地点检索和地理编码均可用。AK 从本地 `.env.txt` 读取，未写入脚本或输出文件。

## 三、处理方法

### 3.1 站点候选获取

对每个站名执行：

```text
query = "站名 公交站"
region = "武汉市"
scope = 2
page_size = 20
```

缓存每次原始响应，重复运行不重复消耗配额。

### 3.2 多候选筛选

每个站点保留最多 12 个候选，综合以下证据：

- 站名相似度；
- 是否为公交车站 POI；
- **站点地址中是否出现当前线路号**（例如 H89 路）；
- 候选所在行政区是否与线路主体一致；
- 相邻站点之间的空间距离；
- 相邻不同站是否被错误选到同一点。

采用动态规划（Viterbi）在整条线路范围内选择一组总成本最低的候选，而不是逐站独立取百度返回的第一个结果。

### 3.3 置信度分级

| 等级 | 条件 | 是否进入网络 |
|---|---|---|
| 高 | 站名相似度 ≥ 0.9、公交站 POI、地址包含当前线路号 | 是 |
| 中 | 站名相似度 ≥ 0.8 且为公交站，或地址包含当前线路号 | 是，建议抽查 |
| 低 | 其他情况 | 否，需人工核验 |
| 未解析 | 无候选 | 否 |

### 3.4 坐标转换与路网吸附

- 百度返回 BD-09，转换为 WGS84 后与 OSM 叠合；
- 只吸附到可行驶道路，排除 footway、cycleway、path、steps；
- 计算站点到最近道路的垂直距离；
- 距离超过 80 米标记异常。

坐标转换是否正确，可通过吸附距离反向验证：如果 BD-09 未转换或转换错误，站点通常会偏离道路数百米。本次中心城区平均吸附距离 2.5 米，说明转换链路正确。

## 五、发现的问题

### 5.1 郊区站名缺失或已改名

示例：

- `陈东路莲湖路` 在百度检索中更接近 `东山大街湖陈路`；
- `三秀路公交停车场` 没有对应的 H89 路公交站 POI；
- `东西湖大道全球保税商品中心` 只检索到商场，没有公交站 POI。

这类站点不能仅靠站名精确匹配解决。

### 5.2 地理编码不能无条件兜底

对 `陈东路莲湖路` 做地理编码，返回的是蔡甸区莲湖路，距离线路数十公里；对 `三秀路荷花园`，地理编码返回的是住宅小区。地理编码结果必须经过路线连续性校验，不能直接采用。

### 5.3 相邻站被选到同一点

当正确站点缺失时，算法可能把两个不同站名选到同一个候选点，造成线路回头或零距离站间距。本次通过线路号证据减少了该问题，但仍需在输出中保留 `zero_leg` 和重复坐标标记。

### 5.4 全量配额压力

公交表共有 694 条线路、6076 个唯一站名。按每个唯一站名一次地点检索估算，全量约需 6000 次请求；若再对低置信度站点做纯站名检索和地理编码兜底，调用量会更高。必须先确认百度控制台的每日配额，并采用缓存、分批和断点续跑。

### 5.5 本次试点已触发百度日配额上限

在完成 340 路、H89 路和少量兜底探测后，百度地点检索返回：

```text
status = 302
message = 天配额超限，限制访问
```

这说明当前 AK 的当日地点检索配额已经用完。该错误不能当作“站点不存在”处理，否则会产生大量虚假的未解析站点。处理脚本已改为：

- 只缓存 `status=0` 的成功响应；
- 遇到配额错误立即停止后续请求；
- 支持 `--offline` 使用已有缓存重跑；
- 下次运行从缓存断点继续。

这也意味着，按 6076 个唯一站名全量调用百度，当前免费配额无法在一天内完成。需要优先确认控制台配额，并考虑按多日分批、申请提高配额，或评估“按线路一次返回全部站点坐标”的替代数据接口，减少调用次数。

### 5.6 替代方案：按线路一次返回全部站点（已验证）

百度地点检索是“按站点查坐标”，没有找到可直接按线路返回全部站点坐标的 Web 服务接口。高德开放平台的“公交信息查询”提供了另一种方式：

```text
https://restapi.amap.com/v3/bus/linename
    ?city=420100
    &keywords=340
    &extensions=all
    &key=<高德Web服务Key>
```

当 `extensions=all` 时，返回的 `buslines[].busstops[]` 包含：

- 站点名称；
- 站点经纬度；
- 站点序号；
- 站点 ID；
- 线路名称、首末站、方向和是否环线。

已使用 `GAODE_KEY` 做小规模验证，结果如下：

| 查询 | 返回方向数 | 单方向站数 | 说明 |
|---|---:|---:|---|
| 340 | 2 | 23 / 24 | 两个方向均返回，站序和坐标完整 |
| H89 | 2 | 59 / 60 | 郊区线路覆盖，站数比 2020 年公共数据多 |
| H82 | 1 | 54 | `loop=1`，环线首尾为同一站 |
| P101 | 2 | 51 / 50 | 首次因 QPS 限制失败，间隔 2 秒后成功 |

结论：

- 一条线路一次请求即可返回全部站点，694 条线路约需 694 次请求，而不是 6076 次站名请求；
- 高德使用 GCJ-02 坐标，需要转换为 WGS84 后再与 OSM 叠合；
- 接口存在 QPS 限制，批量请求需要设置 1.5–2 秒间隔并对 `CUQPS_HAS_EXCEEDED_THE_LIMIT` 做重试；
- 高德当前线路名称、首末站和站数与 2020 年公共数据存在差异，说明线路已更新。应以线路编号和站序为主进行匹配，不能要求站名完全一致；
- 公共数据表仍可作为线路清单和历史对照，高德返回结果可作为当前站点坐标和线路拓扑的主数据源；
- 百度仍保留用于网页底图、地址检索和 POI，不再承担全量站点批量检索。

### 5.7 站点 ID、线路 ID 的含义与更快的发现路径

高德 `lineid` 和 `stopid` 都需要“高德内部 ID”，不是公共数据里的线路号或站名。

| ID 类型 | 示例 | 含义 | 对应接口 |
|---|---|---|---|
| 线路 ID | `900000031144`、`420100014315` | 高德公交线路唯一标识，一个方向一个 ID | `bus/lineid` |
| 站点 ID | `BV11339078`、`BV11169024` | 高德公交站点唯一标识 | `bus/stopid` |
| 公共线路号 | `340路`、`H89路` | 公共数据中的线路名称，不是高德 ID | 需要先转换为高德 ID |

已做的验证：

- `bus/lineid` 使用 H82 环线 ID `420100014315`，返回 54 个站点，`loop=1`；
- `bus/stopid` 使用站点 ID `BV11339078`，返回“东山大街东风大队(公交站)”以及经过该站的 H89、H91 线路和高德线路 ID；
- 这两个接口都是“已知 ID 查详情”，不能按线路名或站名发现 ID。

但 POI 关键字搜索可以完成 ID 发现。使用：

```text
https://restapi.amap.com/v3/place/text
    ?keywords=340路
    &city=420100
    &citylimit=true
    &types=150700
    &offset=20
    &page=1
    &extensions=all
    &key=<高德Web服务Key>
```

返回的不是线路对象，而是沿线公交站 POI。340 路测试结果：

- `count=25`；
- 第 1 页返回 20 个公交站；
- 第 2 页返回 5 个公交站；
- 每个站都有 `BV...` 站点 ID、经纬度和经过线路列表；
- `typecode=150700` 表示公交车站。

因此可以设计一条高配额、可批量执行的链路：

```text
1. place/text 按线路号搜索
   → 分页获取沿线公交站 POI
   → 得到站点 ID、坐标、地址中的线路列表

2. bus/stopid 按任一站点 ID 查询
   → 得到经过该站的所有线路 ID（含两个方向）

3. bus/lineid 按线路 ID 查询
   → 得到该线路完整、带站序的站点列表（权威顺序）

4. 按站点 ID 去重
   → 建立公交站点表和线路-站点关系
```

配额估算：

| 步骤 | 估算调用量 | 配额 |
|---|---:|---:|
| `place/text` 按线路分页（694 条，每条 2–3 页） | 约 1400–2100 | 以控制台基础搜索配额为准，常见为 5000/日 |
| `bus/stopid` 每条线路取一个站点查线路 ID | 约 694 | 10000/日 |
| `bus/lineid` 每个方向一次 | 约 1388 | 5000/日 |

总计约 3500–4200 次请求。按 2 秒间隔约 2–2.5 小时可跑完；如果基础搜索配额少于 2000/日，则分两天执行。所有响应必须缓存，重复运行不重复请求。

注意事项：

- `place/text` 可能返回同名线路的其他站点，需用 `typecode=150700` 和地址中的线路号过滤；
- POI 搜索用于发现站点 ID，**站点顺序以 `lineid` 返回的 `sequence` 为准**；
- 高德当前线路名称和首末站与 2020 年公共数据存在差异，应以线路号+站序对齐；
- 公交关键字查询 `bus/linename` 仍是 100/日，但在这条链路中只作为兜底，不再承担全量发现。

## 七、建议的全量处理策略

### 第一步：先做城市主干线路

优先处理中心城区线路，自动匹配成功率高，可快速形成可用的公交网络骨架。

### 第二步：分批处理郊区线路

按线路或行政区拆分批次，每批完成后检查：

- 高/中/低置信度比例；
- 最大站间距；
- 零距离站间；
- 吸附距离异常；
- 线路是否出现明显回头或跨区跳点。

### 第三步：低置信度人工核验

只对低置信度和异常站点进行人工核验。核验时同时查看：

- 原始站名；
- 百度候选名称与地址；
- 线路号是否匹配；
- 相邻站点位置；
- 站点在 OSM 道路上的吸附位置。

### 第四步：建立全局站点簇

同一物理站点可能被多条线路引用。全量定位后，应按“名称相似 + 空间距离”聚类，生成稳定的 `stop_id`，供公交网络换乘和步行接驳使用。不能只用站名做主键。

### 第五步：再构建多层网络

站点定位完成并通过质检后，才能构建：

- 步行接驳边；
- 公交相邻站边；
- 同站换乘边；
- 地铁线路和换乘边；
- 等时圈与区位指标。

## 八、结论

试点证明“百度补坐标 + OSM 路网叠合”在武汉中心城区可行，且坐标转换和道路吸附链路正确。郊区线路存在站名缺失、改名和 POI 覆盖不足，必须保留置信度分级和人工核验，不能用“全部站点都有坐标”作为数据质量合格的判断标准。

百度地点检索的日配额是硬约束，不能支撑 6076 个站名的全量查询。高德 `bus/linename` 可以按线路一次返回全部站点，但受 100 次/日限制，694 条线路约需 7 天。更快的路径是：用高德 POI 关键字搜索 `place/text` 按线路号分页发现站点 ID，再用 `bus/stopid` 查线路 ID，最后用 `bus/lineid` 获取带站序的完整站点列表；估算约 3500–4200 次请求，对应 5000/10000/5000 的日配额，可在 1–2 天内完成。建议以高德返回的线路和站点为主数据，公共数据表作为线路清单和历史对照，百度保留用于网页底图、地址检索和 POI。批量抓取时必须设置请求间隔、缓存成功响应，并对 QPS 限制和配额错误做显式处理。
