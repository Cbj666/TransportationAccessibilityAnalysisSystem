# 武汉个性化等时圈与区位评估平台

## 项目说明书

版本：v3.0  
课程：GIS 地理信息系统原理与开发  
项目类型：Web GIS 应用开发  
项目组：7 人

## 一、项目概述

### 1.1 项目背景

等时圈表示从指定起点出发，在给定时间成本内能够到达的空间范围。与固定半径缓冲区或统一的“15分钟生活圈”不同，个性化等时圈允许用户设置出行方式、时间预算、步行接驳距离、换乘偏好和评价指标，从而表达不同人群、不同交通条件下的实际可达范围。

武汉受长江、汉江及跨江通道分布影响，不同地点的公共交通连通性和跨区域通行成本存在明显差异。仅分析步行范围难以表现公交线路网络、站点接驳和换乘结构对可达性的影响。本项目将武汉道路网络与公交线路、公交站点等交通数据结合，开发一个支持个性化参数设置、交通可达性计算和候选地点比较的 Web GIS 平台。

### 1.2 项目定位

本项目是一款面向课程教学和地点初步比较的单城市 Web GIS 原型。核心不是评价新城区或老城区的总体生活便利程度，而是回答：

> 在用户指定的出发地点、出行方式、时间预算和偏好条件下，哪些区域与设施可达？不同候选地点的交通可达性和周边资源有何差异？

系统分析链路：

```text
道路、公交线路、站点、POI 数据整理
    → 多方式交通网络构建
    → 按用户参数计算可达范围
    → 生成等时圈和可达路段
    → 统计区域内设施与交通供给
    → 按用户权重生成候选地点比较结果
    → 网页地图交互展示
```

## 二、与“15分钟生活圈”项目的差异

| 对比维度 | 15分钟生活圈评估 | 本项目 |
|---|---|---|
| 核心问题 | 新老城区居民生活便利程度 | 用户设定条件下的地点可达性和区位比较 |
| 分析单位 | 城区、社区或居民生活圈 | 用户指定起点及候选地点 |
| 时间条件 | 通常采用固定 15 分钟 | 用户可设置时间预算和阈值 |
| 交通方式 | 常以步行或生活服务覆盖为主 | 步行接驳与公交网络联合分析；步行单方式作为对照 |
| 公共交通 | 可能不分析公交线路网络 | 纳入公交线路、站点、接驳和换乘成本 |
| 个性化 | 统一评价标准 | 出行参数、设施类别和评分权重可调整 |
| 输出 | 新老城区便利度评价 | 等时圈、可达道路、设施统计、公交供给和候选地点排序 |

本项目不以“新老城区对比”作为主要研究目标，也不将固定 15 分钟生活圈作为唯一分析模式。公交网络和用户可配置的出行条件是主要差异点。

## 三、项目目标与首版边界

### 3.1 总体目标

构建武汉市个性化等时圈和区位评估平台。用户可设置起点、出行模式、时间预算、步行接驳范围和关注的设施类别；系统基于道路网络与公交线路网络生成可达范围，统计可达区域内的设施和交通供给，并对多个候选地点进行可解释的指标对比。

### 3.2 首版必须实现

1. 研究范围限定为武汉市；
2. 提供步行分析，以及“步行接驳 + 公交线路”联合分析；
3. 支持用户设置出行时间预算，默认提供 15、30、45 分钟快捷值；
4. 公交分析使用武汉公交线路、站点及线路连通关系；
5. 计算等时圈或可达节点/路段，并展示公交线路和站点；
6. 统计等时圈内 POI、公交站点和可达道路等指标；
7. 支持至少 2 个候选地点的对比；
8. 提供可调权重的基础区位评分，并展示各维度得分依据；
9. 提供网页端地点设置、参数配置、图层控制和分析结果展示。

### 3.3 首版实现边界

- 公交首版采用静态线路网络和近似时间成本，不承诺实时车辆位置或实时拥堵；
- 如果无法获得完整班次时刻表，候车时间使用明确标注的固定值或线路频率近似值；
- 时间范围以用户选择的总出行预算为准，不固定为某一种“生活圈”标准；
- 区位评分是用户可调整权重下的辅助比较结果，不作为自动投资或选址决策；
- 首版不承诺驾车实时路况、共享单车、地铁完整时刻表或全方式 MaaS 规划；
- 人口、租金、房价等数据未确认前不纳入必做评分项；
- Three.js 动画属于表现增强，核心分析必须在无动画时仍可使用。

## 四、目标用户与应用场景

### 4.1 目标用户

- 比较居住、办公或商业候选地点的用户；
- 关注公交可达性和周边服务设施的城市空间分析人员；
- GIS 课程项目的开发、教学和演示用户。

### 4.2 典型场景

#### 场景一：通勤条件下的居住点比较

用户设定目的地（如工作地点）、可接受通勤时间和公交偏好，选择多个候选居住点。系统比较各候选点的公交加步行通勤时间、可达范围、换乘情况和周边设施。

#### 场景二：公交可达性区位评估

用户选择商业或服务设施候选点，设定 30 或 45 分钟出行预算，查看公交线路覆盖、站点可达性、可达人口或设施代理指标（若数据可用）以及竞争/配套 POI 分布。

#### 场景三：步行与公交方式对照

用户对同一地点分别计算步行和步行接驳公交等时圈，比较不同交通方式带来的覆盖范围、道路可达性和设施数量差异。

## 五、软件需要实现的功能点

### 5.1 起点与候选地点管理

- 地图点击选点；
- 输入地点名称或地址并搜索；
- 支持浏览器定位（可选，需用户授权）；
- 增加、编辑、删除候选地点；
- 为地点设置名称和类型，如居住候选、办公地点、商户候选；
- 地图标记候选点，并在结果面板中保持颜色和编号一致；
- 支持设置一个或多个目的地，用于通勤评估。

### 5.2 个性化出行参数

- 出行模式：步行；步行接驳公交；
- 总时间预算：用户输入或选择快捷值；
- 快捷时间阈值：15、30、45 分钟，可同时显示多个阈值；
- 步行速度：默认值可配置；
- 最大步行接驳距离或接驳时间；
- 最大换乘次数；
- 换乘惩罚时间；
- 候车时间模型：固定候车时间或依据线路频率近似；
- 无障碍/少步行偏好作为扩展参数，首版可通过接驳距离和惩罚值近似表达。

参数界面应提供合理默认值，并显示关键模型假设，避免要求普通用户手动填写过多专业参数。

### 5.3 多方式等时圈与网络分析

#### 步行网络

- 基于 OSM 道路构建步行网络；
- 按道路长度和设定步行速度计算路段时间成本；
- 排除明确不允许步行的道路；
- 计算给定时间预算内可达节点和道路。

#### 公交网络

- 整理公交线路、线路方向、站点和站点顺序；
- 建立步行网络与公交站点之间的接驳关系；
- 将公交乘车路段、步行接驳、候车和换乘时间组合为网络边权；
- 按用户最大步行距离、时间预算和换乘限制搜索可达网络；
- 输出可达公交线路、站点和相应的可达区域；
- 对数据缺失、断线或方向信息不完整的线路提供质量提示。

公交等时圈表示基于所用公交数据和时间成本假设得到的网络可达结果，不表示实时车辆导航结果。

### 5.4 等时圈与交通图层展示

- 同时显示或切换不同时间阈值的等时圈；
- 区分步行可达区域与公交联合可达区域；
- 展示可达道路、公交线路和公交站点；
- 点击公交线路或站点查看名称、线路数等属性；
- 控制道路、公交、POI、等时圈图层显示；
- 提供图例、透明度和图层顺序控制；
- 显示数据日期、出行参数和结果类型。

### 5.5 空间统计指标

对每个候选点和时间阈值计算：

- 等时圈面积；
- 可达道路长度或路段数量；
- 可达公交站点数量；
- 可达公交线路数量；
- POI 总数及按类别统计数量；
- 不同阈值下指标的增量变化；
- 步行与公交联合模式之间的覆盖差异。

如果后续取得可靠人口栅格数据，可增加覆盖人口估算，但不作为首版必要条件。

### 5.6 个性化区位评估与候选点比较

用户可选择评价维度并设置权重。建议首版提供：

| 评价维度 | 可计算指标示例 | 说明 |
|---|---|---|
| 通勤可达性 | 到指定目的地的估算时间、换乘次数、超时惩罚 | 需要设置目的地；可达时间越短得分越高 |
| 公交便利度 | 时间预算内可达站点数、线路数、线路覆盖 | 反映公交网络供给，不等同于服务质量 |
| 生活设施可达性 | 等时圈内医疗、教育、餐饮、商业等 POI 数量 | 类别由用户选择，避免固定生活圈口径 |
| 道路可达范围 | 等时圈面积、道路长度或可达节点数 | 描述空间覆盖，不单独代表地点优劣 |
| 换乘与步行负担 | 换乘次数、步行接驳时间或距离 | 可按用户偏好设置惩罚权重 |

评分采用归一化后的加权汇总：

```text
综合得分 = Σ（归一化指标得分 × 用户设置权重）
```

权重总和应归一化为 100%。结果页面同时显示综合得分和分项指标，不只给出单一排名。对数据缺失的维度应允许关闭或标记为不可用，不得将缺失值伪装成零分。

### 5.7 结果导出与说明

- 导出当前等时圈 GeoJSON；
- 导出候选地点指标 CSV 或 JSON；
- 导出分析参数、数据来源和计算日期；
- 提供可复制的分析摘要；
- 对候车时间、步行速度和公交数据缺失等模型假设作说明。

首版时间不足时，导出功能可降级为下载分析结果 JSON，但候选点对比和分项结果说明应保留。

## 六、数据设计

### 6.1 数据源

| 数据类型 | 候选来源 | 用途 | 优先级 |
|---|---|---|---|
| 道路路网 | OpenStreetMap 武汉数据 | 步行网络、接驳和等时圈 | 必须 |
| 公交线路与站点 | 已有交通数据集、开放交通数据或授权 API | 构建公交网络 | 必须核验；核心差异依赖此数据 |
| 地址与底图 | 百度地图 API | 地址检索、地理编码、网页底图 | 必须 |
| POI | 百度地图 API 或公开数据 | 设施统计和区位评价 | 至少实现若干类别 |
| 行政区边界 | 公开行政区数据 | 数据裁剪和地图定位 | 建议 |
| GTFS/班次数据 | 城市开放数据（如可获得） | 候车时间和时刻表分析 | 可选增强 |
| 人口栅格 | 公开人口数据 | 覆盖人口估算 | 可选增强 |

公交数据是本项目与纯生活圈分析区分的关键依赖。开发早期必须验证武汉公交线路、站点和站序数据的可用性、完整性、坐标系、更新时间和授权条件。全国城市清单中出现武汉不代表数据集已经包含武汉数据；必须检查实际数据目录或 API 返回结果。

### 6.2 公交数据最低要求

首版公交网络至少需要：

- 站点坐标和稳定的站点标识；
- 线路标识和线路名称；
- 线路经过的站点顺序；
- 线路方向信息，若数据可提供；
- 站点间线路连接关系；
- 数据来源和采集/更新时间。

若只有站点和线路几何、没有站序或班次，则只能进行近似网络可达性分析，应明确标注无法精确估计发车等待和实际通勤时间。

### 6.3 数据格式与坐标系

- 原始数据：GPKG、Shapefile、CSV、GeoJSON 或 API JSON；
- 中间分析：GeoPandas、NetworkX 图对象、GPKG/GeoParquet；
- 前端交换：GeoJSON 和 JSON；
- 指标导出：CSV/JSON。

OSM 数据通常为 WGS84，百度地图相关接口可能使用 BD-09 或其他约定坐标。系统需统一坐标转换流程，并对地址点、路网、公交站点和网页图层分别记录坐标系。坐标转换必须通过已知点和地图叠加进行验证。

所有外部数据应记录来源、日期、许可和服务条款。百度 API 的配额和接口能力以实际控制台权限为准。

## 七、分析方法

### 7.1 多层交通网络模型

系统将交通网络抽象为带权图：

- 步行节点：道路交叉口、道路端点和公交站点接入点；
- 步行边：道路相邻节点之间的可步行路段；
- 公交节点：公交站点；
- 公交边：同一线路相邻站点之间的乘车连接；
- 换乘边：同站或邻近站之间的步行换乘连接；
- 权重：通行时间及用户设定的换乘、候车惩罚。

公交综合时间成本可表示为：

```text
总时间 = 步行接驳时间 + 候车时间 + 公交乘车时间
       + 换乘步行时间 + 换乘惩罚时间
```

首版可使用静态平均速度、固定候车时间和固定换乘惩罚构造可解释模型；如获得 GTFS 或可信班次数据，再扩展为按出发时刻计算。

### 7.2 可达性计算

从用户起点映射到步行网络，使用最短时间路径搜索；公交模式下将步行和公交网络通过站点接驳边连接，在用户时间预算及步行、换乘限制下计算可达节点。推荐使用 NetworkX 或适合多模式网络的图算法实现，并通过小规模已知路线进行测试。

### 7.3 等时圈面生成

对可达路段、节点或站点覆盖范围进行空间处理，生成可视化用的等时圈面。面边界属于对网络可达结果的制图表达，需避免让用户误以为边界内每个点都能无障碍直达。地图应同时提供道路/线路图层以解释等时圈形态。

### 7.4 评价指标处理

- 计数类指标按候选地点和时间阈值统计；
- 不同量纲指标在合成评分前进行归一化；
- 越小越优指标（如通勤时间、换乘次数）需反向转换；
- 权重由用户调整并归一化；
- 显示每项原始值、标准化分值和权重；
- 对指标数量较少或数据缺失的情况显示限制说明。

               │                  │
      ┌────────▼────────┐ ┌───────▼──────────┐
      │ OSM/公交/POI数据 │ │ 百度地图服务      │
      │ 网络与空间分析   │ │ 底图/地址/POI     │

| 层级 | 技术 | 职责 |
|---|---|---|
| 前端框架 | Vue 3 + TypeScript | 参数、地点、图层和结果交互 |

| 后端 | Python + FastAPI | 接口、分析任务、结果缓存 |

| 网络分析 | OSMnx、NetworkX | 路网构建、最短时间路径和可达搜索 |
| 数据交换 | GPKG、GeoJSON、JSON、CSV | 原始、中间及输出数据 |

## 九、网页交互设计

### 9.1 页面区域

- 左侧参数面板：起终点、出行模式、时间预算、接驳和换乘设置；
- 中部地图：候选点、等时圈、道路、公交线路、站点和 POI；
- 右侧分析面板：分项指标、综合评分、数据质量说明和候选点对比；
- 顶部状态区：当前数据集、分析模式、数据日期和计算状态。

### 9.2 核心操作流程

1. 搜索或点击地图设置起点，必要时设置通勤目的地；
2. 添加一个或多个候选地点；
3. 选择步行或步行接驳公交；
4. 设置时间预算、最大步行接驳和换乘偏好；
5. 选择关注的 POI 类别并调整评价权重；
6. 执行分析并查看等时圈、道路、线路和站点；
7. 比较候选点的原始指标和加权评分；
8. 查看模型假设并导出结果。

### 9.3 可视化要求

- 用线型、颜色和图例区分步行道路、公交线路和时间阈值；
- 公交线路按线路或线路类别区分，避免颜色过多造成混乱；
- 等时圈面使用透明填充，不能遮挡道路、站点和 POI；
- 选中候选点时突出对应结果，未选中结果降低视觉权重；
- 评分视图同时展示分项原始指标，避免只显示综合排名；
- Three.js 动画可关闭，并提供不依赖 WebGL 的基础地图结果显示。

## 十、验收标准

### 10.1 数据与网络分析

- 可说明武汉道路和公交数据的来源、范围、日期、许可和坐标系；
- 公交数据至少包含线路、站点和站序/连接关系；
- 能构建步行网络及与公交站点连接的联合网络；
- 能对同一地点分别执行步行和公交联合分析；
- 能按至少两个不同时间预算生成可达结果；
- 能显示可达道路、公交线路、站点和等时圈/可达范围；
- 能统计公交线路数、站点数和至少两类 POI 数量；
- 使用小规模人工路线或固定样例检查时间成本和路径结果。

### 10.2 个性化评估

- 至少支持两个候选地点；
- 用户可调整至少三个评价维度的权重；
- 权重归一化后可生成综合比较结果；
- 页面显示分项原始值、分项分数和权重；
- 数据缺失时明确提示，不生成误导性默认排名。

### 10.3 网页与交付

- 用户可设置地点、交通模式和时间参数；
- 用户可控制公交、道路、POI 和等时圈图层；
- 分析期间有加载、成功、失败和空数据状态；
- 能完成一个武汉案例的端到端演示；
- 提交项目说明书、源代码、数据说明、测试记录和约 15 页介绍 PPT。

## 十二、开发阶段与关键决策门

### 阶段一：公交数据可行性核验

- 检查现有数据中是否实际包含武汉线路和站点；
- 核验站点坐标、线路标识、站序、方向、更新日期和授权；
- 若没有站序或可靠连通关系，尽早改用公开数据或申请 API；
- 在公交数据路线未确认前，不进入完整多模式算法开发。

### 阶段二：最小网络样例

- 选择武汉一个城区或交通走廊；
- 建立步行路网和少量公交线路样例；
- 验证步行接驳、公交乘车、候车和换乘时间计算；
- 用地图和人工路径核对结果。

### 阶段三：核心分析与个性化评分

- 扩展到武汉目标范围；
- 生成多个时间预算下的等时圈；
- 接入 POI 与公交供给统计；
- 完成候选地点比较和权重评分。

### 阶段四：网页系统与展示

- 完成地图、参数面板和候选地点管理；
- 接入分析服务和图层数据；
- 完成图表、图层控制、错误状态和结果导出；
- 完成可复现演示案例与 PPT。

## 十三、风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 武汉公交数据不含线路站序 | 无法构建正确公交网络 | 先做数据核验；补采开放数据；必要时限定测试区域并构建可追溯样例 |
| 无班次和发车频率 | 候车时间精度有限 | 用固定候车时间近似并清楚标注，不宣称实时结果 |
| 百度 API 配额或安全限制 | 地址/POI 请求受限 | 前端与服务端 AK 分离、缓存请求、准备离线测试数据 |
| OSM 与百度坐标系不一致 | 图层错位和节点匹配错误 | 建立转换模块并使用多个已知点验证 |
| 多层网络规模过大 | 计算慢、接口超时 | 限定首版分析范围、裁剪数据、构建空间索引和缓存 |
| 个性化权重造成误导 | 综合分数被误解为客观结论 | 显示分项原始值、权重和方法说明，避免“最佳选址”绝对化措辞 |
| Three.js 开发占用时间 | 核心功能延期 | 先完成常规地图图层，3D/动画列为增强功能 |
| 数据许可不明确 | 展示或发布受限 | 记录条款，限制用途，优先采用允许课程研究使用的数据 |

## 十四、预期成果与项目特色

### 14.1 预期成果

- 武汉个性化等时圈与区位评估 Web GIS 原型；
- OSM 道路和公交线路/站点数据预处理流程；
- 步行与公交联合网络分析程序；
- POI/交通供给空间统计和候选地点评分模块；
- GeoJSON、JSON/CSV 分析结果；
- 项目说明书、测试记录和约 15 页项目介绍 PPT。

### 14.2 项目特色

1. 以用户自定义时间和交通偏好取代单一固定“15分钟生活圈”；
2. 将公交线路、站点、步行接驳和换乘成本纳入可达性分析；
3. 支持候选地点比较和可调整权重的区位评价；
4. 分开呈现空间覆盖、交通供给和设施数量，减少单一评分的信息损失；
5. 以 Python 完成可复现的网络和空间分析，以 Web GIS 提供交互展示。

## 十五、结论

本项目以武汉市为研究区域，围绕用户指定起点、时间预算和交通偏好，构建步行与公交联合网络，生成个性化可达范围，并从公交供给、设施可达性、道路覆盖和通勤条件等方面比较候选地点。项目不以新老城区生活圈评价为目标，也不将固定 15 分钟步行范围作为唯一结果。

项目的主要技术与应用价值在于把公共交通网络真正纳入等时圈计算，并让用户能够查看评分背后的指标和权重。首版公交时间采用静态或近似模型，实际结果需结合数据质量和模型假设解释；后续可在获得可靠班次数据后扩展到按出发时刻的公交可达性分析。
