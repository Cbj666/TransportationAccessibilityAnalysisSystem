# 武汉个性化等时圈数据需求与 Python 处理方案

版本：v1.0  
适用项目：武汉个性化等时圈与区位评估平台  
处理路线：Python GIS 与网络分析工具链

## 一、文档目的

本文说明项目首版需要准备哪些空间数据、每类数据至少需要包含哪些字段，以及如何使用 Python GIS 工具完成数据检查、坐标处理、站点定位、道路接驳、网络分析、等时圈生成和结果验证。

项目核心流程为：

```text
OSM 步行路网 + 公交/地铁线路与站点 + POI + 候选地点
    → 数据检查和坐标统一
    → 站点坐标补齐与人工核验
    → 站点接入步行网络
    → 构建步行/公交多层网络
    → 按用户参数计算可达性
    → 生成等时圈并统计区位指标
    → 导出 GeoJSON/JSON/CSV 供网页使用
```

## 二、首版分析范围与功能边界

### 2.1 首版分析目标

- 研究范围：武汉市及必要的周边缓冲区；
- 交通模式：步行、步行接驳公交；
- 时间预算：用户可配置，提供 15、30、45 分钟快捷值；
- 公交模型：基于线路、站点和站序建立静态网络；如无班次数据，候车时间采用可配置近似值；
- 输出：可达区域/等时圈、可达道路、公交线路与站点、POI 统计、候选地点指标比较；
- 不承诺：实时公交位置、实时拥堵、真实出发时刻下的精确候车时间。

### 2.2 分析概念

系统中的公交等时圈是基于静态网络、步行接驳规则和时间成本假设计算的模型结果。若没有发车时刻表或可靠发车频率，结果不能解释为某个具体时刻的精确公交行程时间。

## 三、所需数据清单

### 3.1 必需数据

| 数据 | 建议格式 | 最低要求字段/属性 | 用途 |
|---|---|---|---|
| 武汉道路网络 | GPKG、GeoJSON 或 OSM PBF | 道路几何、道路类型、OSM ID；若有则保留 `foot`、`access`、`oneway` 等属性 | 构建步行网络和等时圈 |
| 公交站点 | CSV、XLSX、GPKG 或 GeoJSON | 站点名称、稳定 ID（若有）、经纬度或可用于地理编码的地址/名称、所属线路 | 站点展示、接驳网络 |
| 公交线路 | CSV、XLSX、GPKG 或 GeoJSON | 线路 ID/名称、线路几何或站点列表；方向、站序为强烈建议字段 | 建立相邻站点间公交边 |
| POI | CSV、GeoJSON、GPKG 或 API JSON | POI 名称、类别、坐标、来源 | 等时圈内设施统计和区位指标 |
| 候选地点 | 用户输入或 CSV | 候选点名称、坐标、地点类型 | 多地点分析和比较 |

### 3.2 建议数据

| 数据 | 用途 | 说明 |
|---|---|---|
| 武汉行政区边界 | 裁剪、地图范围和行政区属性 | 首版可使用公开边界；需记录来源和许可 |
| 地铁线路和站点 | 扩展城市公共交通覆盖 | 可作为公交网络之外的独立交通方式或后续扩展 |
| GTFS/公交时刻表 | 估计发车等待和出行时刻差异 | 获取不到时不阻塞静态网络首版，但必须说明近似假设 |
| 人口栅格 | 覆盖人口估算 | 可选，确认分辨率、年份和授权后再纳入 |
| 地图地址搜索结果 | 起终点地理编码 | 百度地图 API；需处理其坐标系统并保留原始值 |

### 3.3 公交站点表需要重点核对的字段

收到公共数据平台的表格后，检查是否包含：

- 站点名称；
- 站点唯一编号；
- 线路编号和线路名称；
- 行驶方向或上下行标识；
- 线路内站点顺序/站序；
- 站点经纬度；
- 地址、道路名、行政区等可辅助地理编码的字段；
- 数据更新时间、状态或来源说明。

其中，站序或线路几何对于重建公交线路至关重要。只有站点名称和线路关联、没有站序/线路几何时，不能可靠推断相邻站点及实际公交乘车边；只有站点清单时，只能做站点分布和附近站点统计，不能据此计算公交网络等时圈。

```bash

```

主要库职责：

百度地图 API 的 BD-09 坐标转换、调用密钥和配额需要单独处理；不要把服务端密钥写进代码仓库或前端。

## 六、数据处理步骤

### 步骤 1：建立数据清单并备份原始数据

1. 将下载文件复制到 `data/raw/`；
2. 记录文件名、来源 URL/平台、下载日期、授权说明和数据日期；
3. 不在原始文件上直接编辑；
4. 建立 `data_manifest.csv`，记录每个文件包含的内容、坐标系和已知问题。

### 步骤 2：检查 GPKG 图层和道路属性

先读取图层名、几何类型和坐标系，再选择实际道路图层，不预设图层名。

```python
import pyogrio

gpkg_path = r"data/raw/hubei.gpkg"
for layer in pyogrio.list_layers(gpkg_path):
    print(layer)
```

读取后检查 CRS、字段、几何类型、空几何、重复要素和空间范围：

```python
import geopandas as gpd

roads = gpd.read_file(
    gpkg_path,
    layer="实际道路图层名",
    engine="pyogrio",
)
print(roads.crs)
print(roads.geom_type.value_counts())
print(roads.columns.tolist())
print(roads.total_bounds)
```

核实道路类型和步行属性。对 `foot=no`、`access=private` 等限制应按项目规则排除或标记；属性缺失时不要静默假定所有道路均可步行。

### 步骤 3：提取武汉目标范围

1. 准备武汉行政边界或明确的研究区范围；
2. 将道路和边界转换到相同 CRS；
3. 用 GeoPandas `clip` 裁剪；
4. 为防止边缘道路和公交接驳被截断，可先对研究区向外扩展一个缓冲范围，再做最终展示裁剪；
5. 检查长江、汉江跨江通道和重要区域是否在范围内。

```python
study_area = study_area.to_crs(roads.crs)
roads_wuhan = gpd.clip(roads, study_area)
```

### 步骤 4：清理公交和地铁属性表

1. 统一列名和数据类型；
2. 去除首尾空格、全半角差异和明显无效记录；
3. 标准化站名，但保留原始站名字段；
4. 生成内部唯一 `stop_id`、`route_id`，不要仅用站名作为唯一键；
5. 按线路、方向和站序排序；
6. 检查站序重复、断号、重复站、线路名冲突和停运状态；
7. 保留原始字段，新增清洗字段，不要覆盖来源字段。

如果表格有多个 Sheet，应逐 Sheet 检查；如果有合并单元格或线路信息只写在首行，需要先按原始格式规则补齐线路字段，再做排序和匹配。

### 步骤 5：为缺少坐标的站点补充位置

站点表无经纬度时，可以采用以下策略，按优先顺序选择：

1. 检查同一数据平台是否提供站点空间数据或关联接口；
2. 使用 OSM 站点数据按名称、城市和线路信息进行匹配；
3. 使用具有权限的地图地理编码/POI 搜索 API 查询；
4. 对未匹配、同名或置信度低的记录人工核验；
5. 仍无法确定的记录标记为未定位，不参与网络分析。

地理编码查询建议包含城市和对象类别，例如“武汉市 + 站名 + 公交站/地铁站”。同名站点、道路两侧站点和地铁出入口可能产生多个候选，不能只接受 API 的第一个结果。

坐标表至少保存以下字段：

| 字段 | 说明 |
|---|---|
| `stop_id` | 稳定站点标识 |
| `stop_name_raw` | 来源中的原始名称 |
| `stop_name_norm` | 用于匹配的标准化名称 |
| `route_id`、`direction`、`sequence` | 线路关系与站序 |
| `longitude_raw`、`latitude_raw` | 原始服务返回坐标 |
| `source_crs` | 原始坐标系，如 BD-09、GCJ-02、WGS84 |
| `match_source` | OSM、百度 API、人工定位等 |
| `match_status` | 自动匹配、人工确认、未匹配 |
| `review_note` | 歧义和人工检查说明 |

地址匹配结果的置信度可根据名称相似度、行政区、线路名和与已知邻站的空间关系综合检查。地理编码补坐标属于数据定位过程，不等价于精确测绘。

### 步骤 6：统一坐标系并验证位置

1. 路网分析采用适合距离计算的米制投影 CRS；
2. 保存原始经纬度和原始坐标系信息；
3. 将百度 BD-09、GCJ-02 或 WGS84 坐标通过明确的转换函数统一到分析 CRS；
4. 对站点、道路、行政边界进行叠加检查；
5. 抽取武汉不同区域的多个站点，在底图上人工验证；
6. 记录转换函数版本和检查结论。

不要仅修改 CRS 标签。若原始坐标为 BD-09，必须先做坐标值转换，再进行投影变换；`to_crs()` 不能代替 BD-09/GCJ-02/WGS84 之间的偏移转换。

### 步骤 7：处理站点与线路关系

建立规范化表结构：

```text
stops(stop_id, stop_name, geometry, source, quality_flag)
routes(route_id, route_name, direction, source)
route_stops(route_id, direction, sequence, stop_id)
```

处理规则：

- 同名但不同位置的站点保持为不同 `stop_id`；
- 同一物理站点被多条线路使用时，可保留站点实体并在 `route_stops` 中建立多条关系；
- 不同方向站点若位于道路两侧，应分别保留；
- 只有线路几何、无站序时，可通过站点到线路的空间关系辅助检查，但不能仅靠空间排序断言车辆运行顺序；
- 若没有站序或可用线路几何，将公交功能降级为站点覆盖分析，并在界面标明不能进行公交网络等时圈计算。

### 步骤 8：将站点接入步行路网

1. 将站点投影到步行网络 CRS；
2. 使用空间索引寻找最近候选道路边；
3. 计算站点到候选边的垂直距离；
4. 在道路边上找到最近投影点；
5. 将道路边在投影点处拆分，或连接到最近网络节点；
6. 根据接驳距离和步行速度计算接驳边时间；
7. 超过质量控制阈值的站点标记为异常，检查坐标、步行限制或路网缺失；
8. 同时保留原始站点点位和吸附点，便于可视化质检。

接驳距离上限应通过武汉样本测试确定，不应未经验证写死。最近路段通常比最近交叉口更贴近公交站的道路位置；对复杂立交、站内通道和道路隔离情形，需要单独检查。

### 步骤 9：构建带时间权重的多层网络

#### 步行边

```text
walk_time_seconds = edge_length_m / walking_speed_mps
```

如按道路类型设置不同速度，应形成明确配置表并记录依据。首版也可使用统一速度，减少额外假设。

#### 公交边

对同一 `route_id + direction` 下相邻 `sequence` 的站点建立连接。公交边时间可采用：

```text
ride_time = route_distance / assumed_bus_speed
```

如线路几何或路段长度可用，优先据此估计距离；否则记录所采用的估算规则。

#### 候车与换乘

若没有时刻表：

- 使用显式配置的平均候车时间或线路频率近似；
- 设置可配置的换乘惩罚时间；
- 在结果说明中提示误差来源。

建立步行与公交层间的站点接驳边，并对换乘步行距离、最大换乘次数和用户设置的惩罚进行建模。

### 步骤 10：计算个性化等时圈

输入参数至少包括：

```text
origin_id / origin_coordinate
mode = walk | walk_transit
time_budget_minutes
walking_speed
max_access_walk_distance or time
max_transfers
transfer_penalty_minutes
waiting_time_model
```

基本流程：

1. 将起点匹配到步行网络；
2. 若为公交模式，将步行层、公交层和换乘边组合为多层图；
3. 使用最短时间路径算法搜索可达节点；
4. 按用户总时间预算筛选节点、道路和公交边；
5. 对可达线网进行缓冲、融合和边界生成；
6. 同时输出网络要素和等时圈面，避免只保留平滑后的多边形；
7. 对多个时间阈值重复计算或一次搜索后分阈值切片。

步行等时圈和公交联合等时圈应作为不同分析结果标识，不能混为一个未说明的范围。

### 步骤 11：空间统计和候选点评分

对每个候选点、交通模式和时间预算分别执行：

- 计算等时圈面积；
- 计算可达道路长度；
- 统计可达公交线路和站点；
- 对 POI 与等时圈进行空间连接，按类别计数；
- 计算通勤目的地的最短时间、换乘数和步行接驳量（设置目的地时）；
- 对候选点指标进行统一尺度转换；
- 按用户权重计算综合分，并同时保留原始指标及分项得分。

POI 的“落入等时圈”统计是空间覆盖近似，不等于真实服务能力或营业状态。对于线网结果，也可补充统计到 POI 的最短网络时间，作为更贴近交通成本的扩展分析。

### 步骤 12：导出网页成果

建议输出：

| 文件 | 内容 |
|---|---|
| `isochrones.geojson` | 各候选点、模式、时间阈值的等时圈面 |
| `reachable_roads.geojson` | 可达步行道路及时间属性 |
| `reachable_transit.geojson` | 可达公交线路和站点 |
| `pois.geojson` | 展示范围内的 POI 点及类别 |
| `analysis_summary.json` | 面积、道路、公交和 POI 统计 |
| `candidate_scores.csv` | 候选地点原始指标、权重和得分 |
| `analysis_metadata.json` | 数据来源、日期、坐标系、参数和模型说明 |

输出 GeoJSON 的坐标系应与前端地图接口要求一致，并在文件元数据或接口说明中明确坐标约定。百度地图 API 的 AK 应根据应用类型分别管理，服务端密钥不得下发到浏览器。

## 八、质量检查与测试

### 8.1 数据质量检查

- 几何为空、无效或超出武汉范围的道路；
- 不可步行道路是否误纳入；
- 站点坐标是否落在武汉或合理邻接范围；
- 未定位站点、重复站点和同名异地站点；
- 线路站序是否重复、断裂或方向混杂；
- 公交相邻站点间距异常；
- 站点吸附距离异常；
- POI 类别为空、坐标重复或范围错误；
- 每个文件的 CRS 与数据来源是否有记录。

### 8.2 网络结果测试

- 选择已知起点和邻近站点，验证接驳路径合理；
- 手工核对一条公交线路的站序和相邻站点；
- 检查 15 分钟可达结果应包含在 30 分钟结果内，30 分钟结果应包含在 45 分钟结果内；
- 对公交结果检查总时间是否包含步行、候车、乘车和换乘成本；
- 改变步行速度、候车时间或换乘惩罚，确认结果按预期变化；
- 检查输出图层在网页底图上的位置偏差。

### 8.3 结果限制说明

每次分析至少记录：

- 路网、公交、POI 数据来源和日期；
- 起点和坐标转换方式；
- 速度、候车、换乘、接驳等模型参数；
- 线路数据缺失情况；
- 结果属于静态估算而非实时导航的提示。

### 11.2 1:25 万矢量地图

文件：`h50c002001.zip`，解压后为 9 个 Shapefile 图层。

| 图层 | 内容 | 能否用于等时圈 |
|---|---|---|
| `lrdl` | 道路（高速、一级、二级、三级、四级、等外） | 不能，比例尺过粗，缺少步行属性和交叉口连通关系 |
| `lrrl` | 铁路 | 可作为背景或障碍校核 |
| `hyda` | 水域面 | 可作为背景或障碍校核 |
| `hydl` | 水系线 | 可作为背景 |
| `hydp` | 水库/水系点 | 可作为背景 |
| `resa` | 居民地面 | 可作为背景和制图 |
| `resp` | 居民地点 | 可作为背景 |
| `aanp` | 地名注记点 | 可用于制图标注 |
| `agnp` | 行政村/地名点 | 可用于制图标注和空间背景 |

数据特征：

- 坐标系：CGCS2000 地理坐标；
- 分幅范围：约 114°E–115.5°E，30°N–31°N；

推荐用途：

4. 使用地名点图层补充地图标注；
