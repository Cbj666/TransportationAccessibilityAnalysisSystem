# 武汉步行等时圈交通可达性分析平台

## 项目说明书

版本：v2.0  
课程：GIS 地理信息系统原理与开发  
项目类型：Web GIS 应用开发  
项目组：7 人

## 一、项目概述

### 1.1 项目名称

武汉步行等时圈交通可达性分析平台。

### 1.2 项目背景

传统地图通常以道路距离、行政区范围或静态缓冲区表达地点的影响范围，但实际步行可达范围受到道路连通性、河流、铁路、封闭区域和道路等级等因素影响，往往不是规则圆形。等时圈以“从某个起点出发，在给定时间内能够到达的区域”为核心，将交通时间转化为空间范围，能够更加直观地表达城市空间可达性。

武汉市具有长江、汉江分隔，多中心发展和公共交通设施分布不均等特点，适合作为步行可达性分析的案例城市。本项目拟开发一个面向网页端的轻量化 GIS 分析平台，以武汉市路网为基础，计算指定地点在不同步行时间限制下的可达范围，并统计范围内的兴趣点或公交站点数量，为地点周边设施分析和城市空间认知提供辅助工具。

### 1.3 项目定位

本项目是一款面向课程教学和 GIS 应用演示的单城市 Web GIS 原型系统，重点展示以下完整过程：

```text
空间数据获取
    → 路网数据预处理
    → 基于路网的步行时间分析
    → 等时圈生成
    → POI/公交站点空间统计
    → 网页交互式地图展示
```

系统首版不追求实时导航或商业级地图服务，而是突出 GIS 数据处理、网络分析、空间叠加和可视化表达。

## 二、首版范围与边界

### 2.1 首版承诺

首版只承诺以下功能：

1. 分析范围限定为武汉市单城市；
2. 支持步行出行方式；
3. 支持 15、30、45 分钟三个时间阈值；
4. 生成并展示不同时间阈值对应的等时圈；
5. 计算等时圈面积和覆盖道路范围；
6. 统计等时圈内 POI 或公交站点数量；
7. 提供网页端的起点设置、参数选择、图层控制和结果查看功能。

### 2.2 首版不承诺

以下内容不作为首版验收条件：

- 实时道路拥堵和实时步行导航；
- 驾车、骑行和公交等多种出行方式的完整支持；
- 基于真实公交班次、候车时间和换乘时间的公交等时圈；
- 全国多城市分析；
- 租金、房价、人口预测等需要额外数据源的评价指标；
- 商业级地址推荐或自动选址结论；
- 精确到个人实际行走时间的预测；
- 必须使用三维场景或复杂粒子动画才能完成系统展示。

后续可以在首版稳定后增加骑行、公交、人口覆盖、候选地点对比和动态路径动画等扩展功能，但扩展功能不能影响首版核心流程的完成。

## 三、项目目标

### 3.1 总体目标

构建一个基于武汉步行路网的等时圈可达性分析平台。用户输入地点或在地图上选择起点后，系统计算 15、30、45 分钟步行范围，展示可达区域和道路范围，并统计范围内的 POI 或公交站点，为用户理解地点周边的步行可达性提供直观依据。

### 3.2 具体目标

1. 获取并整理武汉市道路网络和相关设施数据；
2. 建立包含道路长度、道路类型和步行速度等属性的路网模型；
3. 使用网络最短路径算法计算起点到路网节点的最短步行时间；
4. 根据时间阈值提取可达节点和道路，生成等时圈面；
5. 使用空间连接或相交分析统计等时圈内设施数量；
6. 将分析结果转换为适合网页加载的 GeoJSON 数据；
7. 使用 Vue、百度地图 API 和 Three.js 完成交互式可视化；
8. 对数据处理、算法结果和前端展示进行测试并形成项目文档。

## 四、用户与应用场景

### 4.1 目标用户

- 需要了解某地点步行可达范围的普通用户；
- 进行城市空间和交通可达性分析的学生或研究人员；
- 需要查看周边设施分布的地点考察人员；
- GIS 课程中的项目展示和教学演示用户。

### 4.2 典型应用场景

#### 场景一：地点周边步行可达性查询

用户输入“武汉大学”或点击地图设置起点，选择步行分析，系统同时显示 15、30、45 分钟等时圈，并标注起点和统计信息。

#### 场景二：周边设施统计

用户打开餐饮、医疗、教育、商业或公交站点图层，系统统计不同等时圈内的设施数量，帮助用户比较不同时间范围内可以到达的设施规模。

#### 场景三：候选地点初步比较

用户依次选择两个或多个候选地点，查看各地点的等时圈面积、覆盖道路长度和设施数量。该功能只提供客观指标对比，不自动给出商业决策结论。

## 五、系统功能设计

### 5.1 地点设置功能

- 地图点击设置起点；
- 输入地点名称或地址进行地理编码；
- 在地图上显示起点标记；
- 支持重新设置和清除起点；
- 显示当前分析地点名称或坐标。

百度地图 API 主要用于地图底图、地址搜索和地理编码。地址搜索结果需要经过坐标系统转换后再与 OSM 路网数据进行匹配。

### 5.2 等时圈分析功能

- 固定支持 15、30、45 分钟三个阈值；
- 将起点匹配到最近的可步行路网节点；
- 根据道路长度和设定步行速度计算道路通行时间；
- 使用最短路径算法计算各节点的最短到达时间；
- 提取不同阈值内的可达节点和道路；
- 生成 15、30、45 分钟等时圈面；
- 显示计算状态、数据日期和模型参数。

### 5.3 空间统计功能

首版至少实现一种设施统计，建议优先实现 POI 统计，并将公交站点统计作为可选的第二类设施。

统计内容包括：

- 各时间阈值等时圈面积；
- 等时圈内道路数量或道路长度；
- 等时圈内 POI 总数；
- 按类别统计 POI 数量；
- 等时圈内公交站点数量（数据准备完成时启用）。

统计结果应明确时间阈值、统计对象和数据日期，避免将数量统计误解为设施服务质量评价。

### 5.4 图层控制功能

- 等时圈图层开关；
- 15、30、45 分钟等时圈分别显示或隐藏；
- 道路图层开关；
- POI 或公交站点图层开关；
- POI 类别筛选；
- 透明度调整；
- 图例显示。

### 5.5 结果展示功能

结果面板显示：

- 当前起点；
- 各时间阈值对应的等时圈面积；
- 覆盖道路长度或道路数量；
- POI 总数及分类统计；
- 公交站点数量（启用时）；
- 步行速度、路网数据日期和结果说明。

图表可使用 ECharts 展示 POI 分类柱状图或不同阈值指标对比图。Three.js 可用于等时圈边界、道路高亮和渐进绘制等视觉增强，但其动画不是系统核心计算条件。

## 六、数据设计

### 6.1 数据源规划

| 数据类型 | 首选来源 | 用途 | 首版状态 |
|---|---|---|---|
| 道路路网 | OpenStreetMap 武汉数据 | 构建步行网络和生成等时圈 | 必须 |
| 地址/地点 | 百度地图 API | 地址搜索和地理编码 | 必须 |
| 地图底图 | 百度地图 API | 网页地图背景和交互 | 必须 |
| POI | 百度地图 API 或整理后的公开数据 | 等时圈内设施统计 | 至少选择一种 |
| 公交站点 | 公开交通数据或百度地图数据 | 公交站点数量统计 | 可选 |
| 武汉行政区边界 | 公开行政区数据 | 裁剪和地图范围控制 | 建议 |

所有外部数据应记录来源、获取日期、坐标系、授权或使用限制。百度地图 API 的具体调用接口、配额和返回字段以实际申请到的服务为准，项目说明书不预先承诺未验证的接口能力。

### 6.2 数据处理格式

- 原始 OSM 数据：GPKG 或其他原始下载格式；
- Python 中间数据：GPKG、GeoParquet 或 GeoDataFrame；
- 路网分析数据：节点表、边表和网络图对象；
- 前端展示数据：GeoJSON；
- 配置和统计结果：JSON。

Shapefile 仅作为桌面 GIS 软件兼容时的交换格式，不作为项目唯一数据格式，以避免字段长度、编码和多文件管理问题。

### 6.3 坐标系处理

OSM 数据通常使用 WGS84 坐标系，百度地图数据通常使用 BD-09 坐标系。系统必须在数据进入分析和数据返回网页时明确坐标转换流程：

```text
百度 BD-09 地址坐标
    → 转换为统一分析坐标
    → 匹配 OSM 路网节点
    → 计算等时圈
    → 转换为网页地图需要的坐标
    → 前端展示
```

坐标转换函数需要使用少量已知点进行验证，检查转换前后距离误差，不能直接把不同坐标系的经纬度叠加。

## 七、等时圈分析方法

### 7.1 路网模型

将道路数据抽象为带权有向图或无向图：

- 节点：道路交叉口、道路端点或经过简化后的路网节点；
- 边：相邻节点之间的道路路段；
- 边长度：由道路几何计算得到；
- 步行速度：根据道路类型设置默认值，或使用统一课程实验参数；
- 边权重：该路段预计步行时间。

基本计算公式为：

```text
步行时间 = 道路长度 / 设定步行速度
```

实际系统应统一使用秒或分钟作为内部时间单位，并在结果展示时转换为分钟。

### 7.2 算法流程

```text
用户选择起点
    ↓
地址坐标转换或地图点击坐标处理
    ↓
匹配最近可步行路网节点
    ↓
计算起点到各节点的最短步行时间
    ↓
筛选时间 ≤ 15、30、45 分钟的节点
    ↓
提取对应路段和节点
    ↓
对可达路段进行缓冲、融合和边界处理
    ↓
生成三个等时圈面
    ↓
与 POI/公交站点进行空间叠加
    ↓
导出 GeoJSON 和统计 JSON
```

推荐使用 Python 的 OSMnx、NetworkX、GeoPandas 和 Shapely 完成上述流程。

### 7.3 结果解释与限制

首版等时圈是基于静态道路网络和设定步行速度计算的模型结果，不是实时导航结果。结果精度受以下因素影响：

- OSM 路网的完整性和更新时间；
- 道路是否允许步行以及步行属性是否完整；
- 道路交叉口和几何简化方式；
- 步行速度设定；
- 河流、铁路、围墙和封闭区域等障碍数据的完整性；
- 起点坐标与最近路网节点之间的匹配误差。

网页和 PPT 中应展示“模型假设”和“数据来源”，避免将等时圈表述为绝对精确的个人行程时间。

## 八、系统技术架构

### 8.1 总体架构

```text
┌──────────────────────────────────────────────┐
│                 Vue 3 前端                   │
│  参数面板｜地图交互｜图层控制｜统计结果｜图表  │
└──────────────────────┬───────────────────────┘
                       │ HTTP / JSON
┌──────────────────────▼───────────────────────┐
│              Python 分析服务                 │
│ 地址处理｜等时圈计算｜空间统计｜结果缓存       │
└───────────────┬──────────────────┬────────────┘
                │                  │
       ┌────────▼────────┐  ┌──────▼──────────┐
       │  空间数据与路网  │  │ 百度地图 API     │
       │ OSM/GPKG/GeoJSON │  │ 地址/POI/底图    │
       └─────────────────┘  └─────────────────┘
```

### 8.2 技术选型

| 层级 | 技术 | 主要职责 |
|---|---|---|
| 前端框架 | Vue 3 + TypeScript | 页面组织和交互状态管理 |
| 网页地图 | 百度地图 JavaScript API | 底图、缩放、地点检索和地图交互 |
| 专题渲染 | Three.js | 等时圈和道路的增强可视化 |
| 图表 | ECharts | 统计结果和指标对比 |
| 后端语言 | Python | 数据处理、分析和服务接口 |
| 空间处理 | GeoPandas、Shapely、PyProj | 裁剪、叠加、几何和坐标处理 |
| 路网分析 | OSMnx、NetworkX | 路网构建和最短路径分析 |
| 接口服务 | FastAPI | 向前端提供分析接口，可选 |
| 数据格式 | GPKG、GeoJSON、JSON | 中间数据和前端交换 |

### 8.3 服务模式

首版可以采用两种实现模式：

1. **预处理结果模式**：提前计算若干示例起点的等时圈，前端直接加载 GeoJSON，适合先完成可视化原型；
2. **动态计算模式**：用户提交起点后由 Python 服务计算并返回结果，适合完成完整交互。

建议先实现预处理结果模式验证前端，再接入动态计算接口，降低开发风险。

## 九、网页交互设计

### 9.1 页面布局

- 左侧：地点设置和分析参数；
- 中部：百度地图与等时圈图层；
- 右侧：统计结果、图例和数据说明；
- 顶部：项目名称、数据日期和当前分析状态。

页面重点应放在地图和分析结果上，不设置与核心功能无关的装饰性页面。

### 9.2 核心操作流程

1. 用户输入地址或点击地图设置起点；
2. 系统完成地址解析和路网节点匹配；
3. 用户点击“开始分析”；
4. 系统生成 15、30、45 分钟等时圈；
5. 地图显示不同颜色和透明度的等时圈；
6. 用户打开 POI 或公交站点图层；
7. 结果面板显示面积、道路范围和设施统计；
8. 用户点击图层或设施点查看属性信息。

### 9.3 可视化规范

建议使用由近到远逐渐变化的颜色，例如：

- 15 分钟：橙色；
- 30 分钟：绿色；
- 45 分钟：蓝色。

三个等时圈应设置适当透明度，避免覆盖底图和 POI。地图中必须显示图例、比例尺或必要的结果说明。

Three.js 的动态效果建议控制在以下范围：

- 等时圈边界渐进显示；
- 可达道路高亮；
- 起点向外扩散的轻量动画。

动画应支持关闭，不得影响地图基本交互和结果阅读。

## 十、项目验收标准

### 10.1 数据与分析验收

- 能够读取并说明武汉路网数据来源、日期和坐标系；
- 能够将用户起点匹配到路网；
- 能够计算 15、30、45 分钟三个时间阈值；
- 三个阈值具有嵌套关系或能解释不满足嵌套关系的原因；
- 能够输出等时圈 GeoJSON；
- 能够计算等时圈面积；
- 能够计算道路数量或道路长度；
- 至少能够统计一种设施数据；
- 结果可以重复计算或由固定测试样例复现。

### 10.2 网页验收

- 用户能够设置或修改起点；
- 用户能够触发分析并看到加载状态；
- 地图能够显示起点、等时圈和设施图层；
- 用户能够切换等时圈和设施图层；
- 结果面板能够显示统计指标；
- 页面在常见桌面浏览器中可以正常运行；
- 数据加载失败时有明确提示，不出现空白页面。

### 10.3 文档与展示验收

- 能够说明数据来源、处理流程和坐标系；
- 能够解释最短路径和等时圈生成方法；
- 能够展示至少一个武汉地点的完整分析案例；
- 能够说明模型假设、数据限制和后续扩展方向；
- 能够形成项目说明书、系统截图和约 15 页项目介绍 PPT。

## 十二、开发计划

### 第一阶段：需求与数据核验

- 确认首版范围和验收标准；
- 检查湖北 GPKG 的图层和坐标系；
- 确认武汉道路数据是否完整；
- 确定 POI 或公交站点数据方案；
- 完成最小测试区域和测试起点选择。

### 第二阶段：数据预处理

- 提取武汉道路数据；
- 清理道路几何和属性；
- 筛选可步行道路；
- 统一分析坐标系；
- 准备 POI/公交站点数据；
- 输出可供分析的中间数据。

### 第三阶段：等时圈算法

- 完成起点到路网节点匹配；
- 完成道路时间权重计算；
- 完成最短路径搜索；
- 生成 15、30、45 分钟可达节点和道路；
- 生成等时圈面并计算面积；
- 完成设施空间统计。

### 第四阶段：网页系统

- 完成 Vue 页面布局；
- 接入百度地图底图和地点搜索；
- 接入预处理 GeoJSON；
- 完成图层控制和结果面板；

## 十三、风险与应对措施

| 风险 | 影响 | 应对措施 |
|---|---|---|
| GPKG 体积较大或图层复杂 | 数据处理慢 | 先检查图层，再裁剪武汉和目标道路 |
| OSM 步行属性不完整 | 等时圈存在误差 | 记录数据限制，设置可解释的默认规则 |
| 百度 API 配额不足 | 地址或 POI 请求失败 | 缓存结果，准备固定测试数据和备用输入 |
| 坐标系不一致 | 图层错位 | 明确 WGS84、GCJ-02、BD-09 转换流程并用测试点验证 |
| 公交数据不完整 | 无法完成公交统计 | 将 POI 统计作为首版必选，公交站点作为可选扩展 |
| 路网分析耗时较长 | 网页等待时间过长 | 先预处理缓存，后续再实现动态计算 |
| Three.js 开发量过大 | 延误核心功能 | 先完成二维等时圈和图层交互，动画作为增强项 |
| 数据授权或服务条款不清晰 | 项目发布受限 | 记录来源和许可，只在课程展示范围内使用 |

## 十五、结论

本项目以武汉市为研究区域，以步行出行方式为首版分析对象，使用 OSM 路网构建步行网络，通过最短路径算法计算 15、30、45 分钟等时圈，并利用空间叠加方法统计等时圈内的 POI 或公交站点。最终结果通过 Vue、百度地图 API、Three.js 和 ECharts 在网页端展示。

首版的核心价值是完成一条可解释、可复现的 GIS 分析链路：从空间数据获取与处理，到网络可达性计算，再到网页交互式表达。系统的计算结果属于基于静态路网和设定步行速度的模型结果，后续可在此基础上扩展骑行、公交、实时交通、人口覆盖和多地点比较等功能。
