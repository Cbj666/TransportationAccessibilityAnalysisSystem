## 一、代码结构

```text
backend/
  app/
    config.py       建模参数（步速、车速、候车、换乘等），一个 dataclass，可被 API 覆盖
    paths.py        全项目路径定义
    graph.py        多模式图构建：路网 + 公交 + 地铁 → scipy CSR 稀疏矩阵
    isochrone.py    单源最短路径、时间面、等值面多边形、路径分解
  scripts/
    build_graph.py          建图 + 缓存（data/processed/graph/v1/）
    run_pilot_isochrones.py 3 个测试点 × 15/30/45 分钟，出 GeoJSON + 图
```

设计要点：

- **站点拆成"街道点"和"站台点"**：街道点 `B-xxx` 与站台点 `P-bus-line-seq` 分离，
  上车一次付一次候车，下车免费。换乘成本因此自然出现，不需要额外的状态位。
- **乘客可以在真实路网上换乘**：下车后走步行网络到另一个站，再上车，全程走同一次 Dijkstra。
- **图规模**：1,015,242 个节点、2,174,254 条有向边（其中步行 2,076,810 条）。
  建图 6 秒，单点单源最短路径约 1 秒，3 个点 × 9 档等时圈全流程 6 秒。
- **等时圈不是凹包**：先算"时间面" `Z(p) = min_n(t_n + |p-n|/v_walk)`（对最近 8 个可达路网节点取最小值），
  再按 15/30/45 分钟切等值面。凹包会给出蜘蛛网状的多边形，时间面更接近真实可达范围。

## 三、试点结果

三个测试点，15/30/45 分钟，步行 + 公交 + 地铁：

| 测试点 | 15 min | 30 min | 45 min |
|---|---:|---:|---:|
| 武汉大学（八一路珞珈山） | 2.31 km² / 16 站 / 1 地铁站 / 595 POI | 14.75 km² / 85 / 18 / 1,414 | 67.37 km² / 365 / 58 / 2,493 |
| 光谷广场 | 2.16 km² / 15 / 3 / 133 | 17.33 km² / 104 / 17 / 685 | 78.22 km² / 399 / 54 / 1,893 |
| 汉口火车站 | 2.37 km² / 19 / 3 / 30 | 21.17 km² / 189 / 33 / 232 | 93.73 km² / 691 / 97 / 974 |

（面积 / 可达公交站 / 可达地铁站 / 范围内 POI）

验收项：

- [x] 15 分钟范围包含在 30 分钟内，30 在 45 内（三个点均为 `True`，代码强制嵌套）；
- [x] 形状沿路网/轨道走廊展开，跨江范围与地铁线走向一致，未见明显错位；
- [x] 时间组成可解释（见下）；
- [x] 输出 GeoJSON（9 个单档文件 + 1 个合并文件，几何全部合法）。

时间构成示例（最短路径逐段分解）：

```text
光谷广场 -> 地铁 28.6 min：步行 6.5 | 接驳 0.3 | 候车 4.0 | 地铁 1.6 | 候车 4.0 | 地铁 12.2
汉口火车站 -> 地铁 29.8 min：步行 7.4 | 接驳 0.1 | 候车 4.0 | 地铁 6.6 | 候车 3.0 | 地铁 8.7
武大 -> 地铁 29.9 min：步行 17.0 | 接驳 0.1 | 候车 4.0 | 地铁 8.8
```

能看到"先走 7 分钟到站、等 4 分钟、坐 1.6 分钟、换乘再等 4 分钟"这类真实结构，
而不是简单的半径圆。

## 五、已知问题

1. **等时圈有"飞地"**：个别远郊区域通过一条公交线可达，会形成孤立的斑块。
   这在真实可达性里是成立的，但地图上观感一般。若需要，可只保留面积 ≥ 1 km² 的连通块。
2. **15 分钟圈偏小**（2.1–2.4 km²）：因为步行 15 分钟本身只有约 3.7 km² 的理论上限，
   而公交要等 8 分钟，短时间预算下公交贡献有限。这是模型假设的结果，不是 bug。
3. **公交候车统一 8 分钟**：没有逐线路发车间隔，只能全局近似；地铁已按线路区分。
4. **站点接驳用最近路网顶点**：中位误差 30 m（路网顶点间距约 41 m），
   对 15 分钟圈有约 25 秒的系统偏差，后续可改为"投影到路段并打断边"。
5. **POI 稀疏**：汉口火车站 15 分钟圈内只有 30 个 POI，是 OSM 覆盖问题，不是算法问题。
